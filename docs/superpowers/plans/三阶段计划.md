## 一、上一三阶段开发结论

原三阶段方案（2026-08-01）以「融合式创作」为主线，执行结论如下。

### 阶段一：融合式创作闭环——已完成

- 空白、模板、AI 三种创建入口统一进入同一编辑器。
- 统一大屏文档、组件模型和编辑命令，AI 生成、模板创建与手工编辑完全兼容。
- 编辑器核心能力：画布、组件库、拖拽缩放、图层、对齐吸附、撤销重做、样式配置、数据绑定、参数联动、预览和发布。
- 发布安全地址同时支持直接播放和 iframe 嵌入，并支持域名/IP 访问限制。
- 建立纯手工创作与手工/AI 交替协作的端到端测试。

### 阶段二：生成质量与实际可用性——已完成

- 文件数据集（CSV、Excel、JSON、Parquet）与 DuckDB 只读查询。
- AI 数据分析、图表建议、整屏草稿生成和编辑器内 AI 局部修改。
- 5 个内置模板、21 类内置组件、演示/静态/mock 数据统一运行时。
- 数据库刷新、超时、失败隔离、缓存和大数据量限制。
- 三浏览器完整 E2E、跨浏览器视觉门禁全部通过。
- 验收代码基线 `08adadb`，证据见仓库 `docs/PHASE_TWO_CLOSEOUT.md`。

### 阶段三：成熟的人机协同工具——未按原方案完成

- 2026-09-09 后产品路线调整为四阶段：第三阶段改为数字人播报，第四阶段为产品成熟度与生态。
- 原阶段三的「稳定兼容规范、AI 协作质量评估体系、模板质量体系」未系统建立。
- 数字人播报功能与本地回归已完成；真实供应商、目标环境与生产成熟度门禁仍阻塞。
- 第四阶段的身份权限、离线市场、插件 SDK、备份恢复和运维能力已实现并通过本地验证；八项目标环境门禁（P4-ENV-001～004、P4-DH-001～004）全部阻塞，0 项通过（`docs/PHASE_FOUR_CLOSEOUT.md`）。

### 执行中暴露的核心问题

原方案把「提高生成质量」写成模糊目标，没有可验收标准和改造路径，导致关键缺陷没有被任何阶段真正承接：

1. **AI 整屏生成不够智能，且经常创建不出来。**
2. 失败机制是「一次性自由生成 + 全量严格校验 + 失败即 422」：12 个组件中只要有 1 个越界、图表不匹配或缺少绑定，整屏即作废，不重试、不降级、不说明原因。
3. 数据上下文过薄：只有字段名、基础类型和最多 100 行样例，没有字段角色、基数、空值率和分布。
4. CSV 字段几乎全部退化为 `string`（`filedata/parsers.py:175`），模型看不到数值字段，聚合选择必然失准。
5. 布局坐标由模型自由生成，越界和重叠高发，且只检查越界不检查重叠（`screen_generator.py:376`）。
6. 组件上限写死 12（`screen_generator.py:30`），复杂大屏装不下。
7. 屏幕级多源**已经支持**：一块大屏的不同组件可以分别绑定数据库、文件和 HTTP API。但单个图表只能绑一个数据集，跨源合并没有明确的产品出口和上游约定。
8. AI 与核心流程强耦合，不配置 AI 时用户没有任何生成辅助。
9. 组件只有 21 类且偏基础，缺大屏常用的轮播、堆叠、双轴、地图下钻、关系图等。
10. 生成质量没有任何度量，改好改坏无法判断，模型升级无法守住底线。

### 本结论如何引出新方案

上述问题分成四层，必须分开解决：

- **可靠性**（出不出得来）：机制缺陷，不改数据模型就能修。
- **智能性**（出得好不好）：架构缺陷，必须引入「规划 → 编译」中间层。
- **数据能力**（能不能回答真实业务问题）：能力缺陷，必须提升屏幕级多源（多源混合大屏）的生成与编排能力。
- **产品形态**（能不能轻量交付）：耦合缺陷，必须把 AI 变成可选模块。

因此新三阶段主线为「**多源大屏 → 可信生成 → 交付**」，先可靠、再专业、后可托付。数字人阶段和目标环境门禁作为并行轨道保留，不占主线。

> **范围声明：** 一个组件只绑一个数据来源。跨源合并**在上游完成**（源库视图 或 上游接口），DataPulse 通过数据集消费结果；单张图表跨数据集 join 明确不做。详见第六节。

## 二、新方案总纲

### 2.1 三条主线

| 主线 | 解决的问题 | 贯穿阶段 |
| --- | --- | --- |
| 生成可靠性 | 经常创建不出来 | 第一阶段 |
| 生成质量 | 出来得歪、不专业 | 第二阶段 |
| 多源与可托付 | 多源大屏编排不足、不能轻量部署、会退化 | 第二、三阶段 |

### 2.2 四个关键决策

**决策一：跨源合并上移到上游，一个组件只绑一个来源。**

- 基本立场：**一个图表组件就是一个数据来源**。需要多个来源时，不在一张图里硬 join，而是在上游先合并好。
- 推荐做法：源库建视图/物化视图，或由后端开发接口，DataPulse 通过数据集消费结果。
- 已具备通路：HTTP API 数据集（`contracts/dataset.py:43` 的 `RestQuery`）就是这条路径的现成载体，无需改造。
- 继续增强：屏幕级多源的数据集组织、按源分区的编排、跨源一致的时间与维度口径提示。
- 明确不做：单张图表跨数据集 join。
- 理由：合并是数据工程而非可视化；上游最懂关联口径，也能建视图、加索引、做缓存；这与路线中「不做 ETL、不建数仓、不做跨库事务」的边界一致。
- 预留：DataPulse 内的「派生数据集」仅在自助场景（一个主库 + 几个 Excel 且无开发资源）和资源允许时再做，不在本三阶段范围。

**决策二：AI 做成编译期可选模块，不拆独立服务。**

- 核心与 AI 之间有明确接口，AI 关闭时入口隐藏、功能完整。
- 部署形态：最小部署单镜像无 AI；完整部署加 AI 配置。
- 理由：路线明确不引入微服务和分布式中间件；编译期模块边界已能实现「可剥离」，保留将来独立拆包的可能。

**决策三：取消 12 组件写死上限，改为分区约束。**

- 由「怕模型输出太多」改为「保证版面不挤」。
- 总组件数放宽到 40，与路线文档「单大屏建议不超过 40 个可视组件」一致。
- 约束下移到分区、最小尺寸和密度检查。

**决策四：组件分三批扩充，先补大屏刚需。**

- 第一批补轮播/堆叠/双轴/跑马灯等大屏常用，配合第二阶段模板骨架。
- 第二批补地图下钻、关系图、甘特等业务图表。
- 第三批按场景需求驱动。

### 2.3 总体架构

```text
数据接入层
  数据库 / 文件 / HTTP API
        ↓
数据语义层（新增）
  字段画像 · 数据集 · 字段修正
        ↓
规划层（新增，AI 可选）
  DashboardPlan  ← AI 生成 或 手工创建
        ↓
编译层（新增，确定性）
  分区网格 · 模板骨架 · DocumentCompiler
        ↓
校验层（增强）
  查询预执行 · 语义检查 · 视觉检查 · 自检报告
        ↓
交付层（复用现有）
  编辑器 · 发布 · 独立播放 · 数字人 · 嵌入 · 权限
```

**关键：规划层以上全部与 AI 解耦。AI 只是 `DashboardPlan` 的一个生产者。**

### 2.4 AI 可选边界

| 能力 | 归属 | 无 AI 时 |
| --- | --- | --- |
| 数据源 / 数据集 / 画像 / 多源编排 | 核心 | 完整可用 |
| 编辑器 / 绑定 / 发布 / 嵌入 | 核心 | 完整可用 |
| 规则推荐（图表、聚合、角色） | 核心 | 完整可用，不需要模型 |
| 自然语言生成 Plan | AI 模块 | 入口隐藏，改为手工搭建 |
| 自然语言局部修改 | AI 模块 | 入口隐藏，改为手工编辑 |
| 数字人话术生成 | AI 模块 | 回退静态/手写话术 |

## 三、第一阶段：稳定生成

**一句话目标：** 用户提供结构化数据（单源或多源），稳定产出一份可编辑、可发布的可用草稿。

**进入条件：** 现有编辑器、运行时、发布和嵌入链路保持可用。

### 3.1 输入侧：让系统真正看得懂数据

**3.1.1 重建文件类型推断**

- 现状：`_parse_csv`（`filedata/parsers.py:175`）用 `csv.DictReader`，所有值为字符串；`_merge_type`（`parsers.py:106`）因此只能给出 `STRING`。
- 做法：抽出统一类型推断器，对样本逐列扫描，识别 integer / number / boolean / date / datetime / string；列内冲突按「数值优先 → 时间优先 → 字符串兜底」收敛，与 Excel/JSON/Parquet 的 `DatasetField` 语义对齐。
- 交付：类型推断器 + 单测 + CSV 类型回归样例。

**3.1.2 新增 `DatasetProfile` 数据画像**

- 字段级：类型、角色（时间 / 维度 / 指标 / 地理 / 标识 / 文本）、基数、空值率、min/max、TopN、样例值。
- 数据集级：行数、时间覆盖、疑似主键、候选时间字段、指标候选、疑似地理字段。
- 角色判定用确定性规则优先（类型 + 命名 + 基数 + 唯一性），AI 仅在规则无法判定时兜底。
- 交付：画像服务 + 画像 API + 编辑器画像展示。

**3.1.3 字段修正入口**

- 允许用户修改字段类型、角色、默认聚合、单位、显示名。
- 修正结果持久化，参与后续所有生成与推荐。
- 交付：字段编辑面板 + 持久化。

**3.1.4 上下文预算治理**

- 现状：`ai/context.py:104` 全量拼接，最多 8 数据集 × 100 行 × 50 字段。
- 做法：默认只发画像摘要 + 按问题筛选的字段；需要样例时按需取；超预算先降采样再转摘要。

### 3.2 生成侧：把失败率打下来

**3.2.1 结构化输出**

- `ai/gateway.py:59` 从 `{"type": "json_object"}` 升级为 `json_schema` strict，provider 不支持时回退并缓存能力探测结果。

**3.2.2 生成—校验—修复循环**

- 校验失败时把结构化错误（组件 id、字段、原因、期望）回喂模型，最多 2 轮。
- 连续失败才向上报错，并保留最后一次错误与原始输出用于诊断。

**3.2.3 组件级降级**

- 非法组件丢弃或转占位并附 warning，不再整屏 422。
- 设下限：至少一个可渲染组件，否则才判定整体失败。

**3.2.4 独立超时与重试**

- 整屏生成独立超时 60～120 秒，与单图表分析分离。
- 区分超时、限流 429、5xx、4xx，给不同退避与提示。

**3.2.5 错误码细分与可操作提示**

- 新增稳定错误码：`AI_FIELD_UNKNOWN`、`AI_FRAME_OUT_OF_BOUNDS`、`AI_VISUAL_MISMATCH`、`AI_BINDING_MISSING`、`AI_COMPONENT_UNKNOWN`、`AI_TIMEOUT`、`AI_RATE_LIMITED`、`AI_DATASET_INVALID`。
- 前端提示到「哪个组件、哪个字段、为什么、怎么改」，替换现有 `ai/api.py:26` 的笼统英文提示。

**3.2.6 布局合法性补齐**

- 新增组件重叠检测（补齐 `screen_generator.py:376` 只查越界的缺口）。
- 新增最小可读尺寸与文本溢出预估检查。

**3.2.7 组件上限改造**

- 移除 `_MAX_COMPONENTS = 12`（`screen_generator.py:30`）。
- 改为分区约束 + 总数组件 ≤ 40 + 密度检查。
- prompt 同步改为分区描述，而不是单纯数字上限。

### 3.3 度量侧：建立质量基线

- 固定 golden 数据集与问题集，覆盖经营、运营、销售、设备场景，含中文字段名、混合类型、脏数据、单表与宽表。
- 采集指标：首次成功率、失败原因分布、字段绑定准确率、图表类型合理率、警告数、生成耗时、token 成本。
- 用目标模型跑一轮真实基线并归档，作为后续改造对照。

### 3.4 第一阶段验收

- golden 集首次生成成功率 ≥ 90%。
- 生成失败时 100% 仍产出可编辑草稿。
- CSV 数值/日期列类型识别正确率 ≥ 95%。
- 字段绑定准确率有基线且 ≥ 85%。
- 每次失败都能定位到具体组件和字段。
- 组件数可超过 12（验证 ≥ 25 个组件的大屏可生成）。
- 质量指标可一键复跑。

## 四、第二阶段：专业生成

**一句话目标：** 生成结果语义正确、视觉专业，用户只需少量改动；同时增强多源大屏的组织与编排能力。

**进入条件：** 第一阶段门禁通过，质量基线可用。

### 4.1 规划层

**4.1.1 `DashboardPlan` 中间表示**

- 内容：目标受众、叙事结构（总览/趋势/对比/明细）、分区（region）、每个 widget 的意图（**单一数据集来源**、指标、维度、聚合、图表类型、筛选、标题）、全局参数。
- **明确不含像素坐标。**
- **每个 widget 只引用一个数据集。**

**4.1.2 规划生成与校验**

- AI 基于 `DatasetProfile` + 用户描述产出 Plan。
- 服务端校验：字段存在、聚合与类型匹配、图表形状合法（复用 `screen/chart_query.py:42`）、指标不重复、分区数合理、数据集存在且已授权。

**4.1.3 规划可预览可修改**

- 用户先看到「将要生成什么」，可增删指标、换图表、调分区，再触发编译。
- 对应原方案一直未落地的「生成前数据理解确认」。

### 4.2 编译层

**4.2.1 网格与分区系统**

- 12 或 24 栅格，固定行高基准与安全边距，分区到 `frame` 的确定性映射。

**4.2.2 `DocumentCompiler`**

- 输入 `DashboardPlan` + 模板骨架 + 画像，输出 `DashboardDocument`。
- 同一 Plan 必须得到同一布局，可复现、可快照测试，从根上消除越界、重叠、错位。

**4.2.3 模板锚定**

- 把 5 套内置模板抽象为「布局骨架 + 组件槽位 + 主题令牌」，AI 选骨架并填充内容。
- 模板随组件扩充同步更新，新模板必须带样例数据和视觉回归。

**4.2.4 默认值与视觉规范**

- 统一字号阶梯、间距、配色、图表主题、数字格式；文本按容器自适应。

### 4.3 有效性校验

- 编译后每个 `chart_spec` 实际执行一次，复用 `ChartQueryCompiler`、`FileQueryCompiler` 和现有预览路径（`ai/service.py:289`）。
- 空结果、非法聚合、字段缺失 → 回退取图或降级为占位 + warning。
- 语义检查：时间配趋势、类别配占比/排名、单值配 KPI；检测重复图表、无意义聚合、指标维度倒置。
- 视觉检查：重叠、溢出、过小、对比度、留白、密度。
- 生成自检报告：字段、聚合、过滤、实际行数和潜在问题。

### 4.4 多源大屏生成（本阶段增强）

详见第六章。本阶段需完成：屏幕级多源的组织与检索、按来源分区的编排、跨源口径提示、多源生成的组件来源校验。

**明确不做：单张图表跨数据集 join。** 需要合并时走上游（源库视图或上游接口）。

### 4.5 迭代式修改

- 自然语言整屏修改：换风格、换图表、突出异常、调整分区。
- 修改走同一条「Plan → Compile」路径，保证手工与 AI 结果结构一致。
- 局部重生成：只重编受影响分区，不整屏重来。

### 4.6 显示适配

- 覆盖常见分辨率、全屏电视、普通窗口和 iframe 容器。
- 解决「窄屏不溢出但不可读」：最小字号、密度断点、缩放策略。

### 4.7 第二阶段验收

- golden 集：空图表 = 0、组件重叠 = 0、组件越界 = 0。
- 首次生成可用率 ≥ 95%，生成后平均修改组件数 ≤ 2。
- 语义匹配准确率 ≥ 95%。
- 同一 Plan 编译结果确定可复现。
- 至少 3 个多源大屏场景端到端跑通（如「主库组件 + Excel 组件 + 接口组件」同屏）。
- 组件库第一批扩充完成并进入模板。

## 五、第三阶段：可信生成

**一句话目标：** 长期不退化、覆盖真实业务、能轻量交付并可演进。

**进入条件：** 第一阶段与第二阶段门禁全部通过。

### 5.1 质量体系与回归门禁

- 建立生成质量评测 harness：固定数据集、固定问题、多 provider / 多模型横向对比。
- 模型升级门禁：新模型指标不得劣化，否则不允许切换默认模型。
- 持续指标看板：成功率、绑定准确率、语义匹配率、耗时、成本趋势。
- 失败样本库：把评测中的失败固化为回归用例。

### 5.2 数据语义层

- 字段标签、单位、格式、同义词、业务别名。
- 计算字段与指标口径：受控表达式，不执行任意代码。
- 同数据源内关联、维度层级、时间层级。
- 数据质量提示：高空值、异常值、重复、口径冲突。

### 5.3 场景扩展

- 多数据集组合与筛选联动。
- 时间粒度切换（日/周/月/季/年）。
- 行业场景包：经营分析、运营监控、销售分析、设备监控，每个都带样例数据与验证。
- 参数驱动与下钻。

### 5.4 AI 可剥离与轻量交付

详见第七章。本阶段需完成：

## 六、跨源数据策略（专项）

### 6.1 基本立场

**一个图表组件只绑一个数据来源。**

大屏层面已经支持多源：一块大屏的不同组件可以分别绑定数据库、文件和 HTTP API 数据集（屏幕级多源）。真正要明确的是：**单个组件不承担跨源合并**。

需要多个来源的数据出现在同一张图里时，合并**在上游完成**，DataPulse 只负责消费合并后的结果。

### 6.2 三层策略

| 层级 | 谁来做 | 适合场景 | 本三阶段 |
| --- | --- | --- | --- |
| 推荐：源库视图 / 物化视图 | DBA | 同一数据库、可改库结构 | 只需文档说明 |
| 推荐：上游接口 | 后端 | 跨系统、含业务逻辑 | 只需文档说明 |
| 支持：HTTP API 数据集 | DataPulse 用户 | 消费上游接口 | 已有能力，无需改造 |
| 预留：派生数据集 | DataPulse 用户自助 | 主库 + 几个 Excel，无开发资源 | 不做 |

### 6.3 推荐路径：上游合并

**路径一：源库视图 / 物化视图**

- 由 DBA 在源库内建视图，把关联、口径和聚合固化下来。
- DataPulse 通过 TableQuery 或 SqlQuery 直接消费。
- 优点：性能最好，口径统一，DataPulse 侧零复杂度。

**路径二：上游接口**

- 由后端开发接口，把跨系统合并和业务逻辑封装在服务里。
- DataPulse 通过 HTTP API 数据集消费。
- 这是生产环境的正确默认做法。

### 6.4 支持路径：HTTP API 数据集

这条通路**已经具备，无需改造**（`contracts/dataset.py:43` 的 `RestQuery`）：

- 方法：GET / POST
- 查询参数、POST JSON body
- 用点号路径取嵌套响应，如 `data.items`
- 鉴权：无认证 / Bearer / API Key / Basic
- 响应形态：对象数组、单对象或标量
- 限制：5 MB 响应体、5000 行、300 秒超时

**上游接口要遵守的约定**（新增文档内容）：

1. 返回扁平的对象数组，字段名与类型稳定；避免混类型和大量 null，否则字段类型推断会退化。
2. 支持参数化筛选（时间、地区等），避免大屏拉全量。
3. 控制响应体在 5 MB 以内。
4. 明确鉴权方式，并在 DataPulse 中配置对应凭据类型。
5. 注意网络约束：DataPulse 不跟随重定向，要求同协议、同主机、同端口，并拦截 localhost 与内网字面量地址；接口部署位置需匹配。
6. 上游接口可用性直接影响大屏，需要有基本可用性保障。

### 6.5 预留路径：派生数据集

仅在自助场景（用户手上有「一个主库 + 几个 Excel」但没有开发资源）且资源允许时才考虑。

- 形态：新增一种数据集类型，产出仍是普通数据集，**`ChartSpec.dataset_id` 不需要改**。
- 好处：编辑器、组件、运行时、发布、嵌入、AI 全部零改动，复杂度收敛在数据集层。
- 代价：需要 `DatasetDefinition.schema_version` 从 `Literal[1]` 演进并迁移；还要处理字段重名别名、类型对齐、下推策略、发布依赖递归、双侧权限校验和缓存键版本。
- 结论：不在本三阶段范围，但架构上保留这条口子，不堵死。

### 6.6 屏幕级多源仍需增强的部分

- 多源数据集的组织与检索，避免数据集变多后难以选择。
- 按来源分区的编排：让「同一来源的组件放在一起」成为模板的一种布局策略。
- 跨源一致的时间与维度口径提示：当同一大屏中不同来源的时间字段粒度不一致时给出提醒。
- 多源生成的校验：确认每个组件的 `dataset_id` 指向真实存在且已授权的数据集。

## 七、AI 可剥离设计（专项）

### 7.1 模块边界

**核心模块（永远存在）**

- datasource、dataset、profile、relation、query、screen、runtime、publishing、embedding、identity、operations。

**AI 模块（可选）**

- `ai/gateway`、`ai/service`、`ai/screen_generator`、`ai/context`。
- 职责仅三件：从画像+描述生成 `DashboardPlan`、生成局部修改命令、生成数字人话术。

**接口契约**

- AI 的输出必须是 `DashboardPlan` 或编辑命令，且经过与手工路径相同的服务端校验。
- 核心模块不 import AI 模块；由装配层按开关注入。

### 7.2 两种部署形态

| | 最小部署 | 完整部署 |
| --- | --- | --- |
| 镜像 | 单镜像 | 单镜像 |
| AI 配置 | 无 | 有 |
| 数据源/多源 | 完整 | 完整 |
| 编辑器/发布/嵌入 | 完整 | 完整 |
| AI 生成/对话 | 入口隐藏 | 可用 |
| 规则推荐 | 可用 | 可用 |

### 7.3 关闭 AI 时的行为

- 「AI 生成大屏」入口整个隐藏，而不是点进去报错。
- AI 相关 API 不挂载或直接返回稳定的未配置状态。
- 编辑器提供规则推荐：推荐图表类型、推荐聚合、标注字段角色、提示可疑字段。
- 数字人回退手写话术与静态字幕。

### 7.4 不引入双套逻辑

- 手工与 AI 都产出 `DashboardPlan`，共用编译器和校验器。
- 手工路径不允许绕过校验，AI 路径不享受特权。

## 十二、风险与不做清单

**主要风险**

1. 上游合并方案若口径不统一，会导致同一指标在不同大屏口径不一致 → 在文档中明确上游接口约定，并提供口径说明入口。
2. 编译器若过度刚性会导致布局单调 → 骨架多样化 + 允许手工覆盖。
3. 画像可能误判 → 一律可人工修正，且修正结果优先。
4. 组件扩充若缺规范会失控 → 强制统一属性、默认样式、测试和模板同步。
5. AI 剥离若边界不清会退化成两套逻辑 → 强制共用 Plan 与校验器。

**明确不做**

- 单张图表跨数据集 join（跨源合并上移到上游，见第六节）。
- DataPulse 内的派生数据集（仅预留，不在本三阶段范围）。
- ETL、数仓、数据质量平台。
- 行列级、部门级权限。
- 3D 数字孪生与 Cesium GIS。
- 移动端独立编辑器。
- 微服务与分布式中间件。
- AI 执行任意代码或未经确认自动发布。
