# Processing isolation and capacity

Uploaded CSV, Excel, JSON and Parquet decoding, Excel sheet enumeration, and image decoding/thumbnail generation run in fresh subprocesses. File parsing copies the immutable upload into a private staging directory, validates the worker's bounded JSON response, and atomically installs any normalized CSV/Parquet output. Failure or cancellation removes staging and preserves the original upload. Images use private temporary input files and return validated metadata plus a bounded PNG thumbnail. No upload bytes are decoded by the API's thread pool for these paths.

Repeated file reads reuse validated parse results in an LRU cache capped at 64 entries and 8 MiB of serialized data per event loop. The key includes the resolved source path, device/inode, size, modification/change timestamps, format, Excel sheet and preview row limit. Every reuse checks regular-file status and source/normalized-file fingerprints; deleting, replacing or changing either file invalidates reuse. Concurrent readers of the same key share one subprocess. Cancelling one reader leaves processing available to the others; cancelling the last reader terminates and reaps the processor before returning. Completed cache entries contain only serialized bytes and filesystem metadata, so closed loops are not retained. Caches are local to each API process; the two shared processor slots still limit cold parses across processes. Saturation by unrelated files returns `429 FILE_PROCESSING_BUSY`, and runtime decoding failures return `422 FILE_PARSE_INVALID`.

`operations/process_runner.py` applies CPU, output-file-size and core-dump limits before executing the processor without a shell. Linux also enforces an address-space limit. The default parser has a 30-second wall/CPU budget, 1 GiB address-space limit on Linux, 512 MiB output-file limit, 8 MiB per stdout/stderr pipe, and two processing slots shared through per-user temporary-directory file locks. NumPy/OpenBLAS/OpenMP thread counts are fixed at one. Arrow uses its system memory pool and glibc is limited to two allocation arenas so allocator reservations do not exhaust the address-space budget on small Parquet inputs. Parser subprocess environments contain only the explicitly allowed locale/path/temp/timezone values, thread caps and allocator settings; database credentials, master/signing keys and cloud credentials are not inherited. Image wall time follows `DATAPULSE_MEDIA_TIMEOUT_SECONDS` and media concurrency also uses existing asset-directory processing locks.

Timeout, cancellation and oversized pipe output terminate the process group, drain pending bounded pipes and reap the child before releasing the processing slot. A process failure or resource-limit exit does not return a partial successful parse. The parser response is validated in the API before a normalized file is installed. Source and staging files have restricted access; the parent only accepts a regular normalized file directly inside the private staging directory.

FFmpeg/FFprobe and the configured antivirus adapter use the same resource-limiting launcher. The scanner runs before uploaded files are parsed or published and before media decoding. Scanner exit `0` means clean, `1` means rejection, and other exits, timeout or unavailability fail closed. Configure a real local scanner using `DATAPULSE_UPLOAD_SCANNER_COMMAND` as a JSON argument array; do not construct a shell command from an upload filename. A scanner is disabled when the command is empty. Production validation must confirm the scanner binary/signatures, supported formats, resource budget and actual detection behavior. Fake test executables do not establish malware-detection efficacy or pass P4-DH-004.

## Boundaries that remain deployment responsibilities

This is process and resource isolation, **not a security sandbox**. Children still run as the service user and can access filesystem/network resources allowed to that user. There is no per-job UID, chroot, seccomp policy, mount/network namespace or container isolation. A compromised native decoder could read accessible secret files or reach the network, even though secret environment variables were removed. Process-group cleanup cannot contain an exploited child that deliberately escapes its group. Run the service and processors as a dedicated non-root account in a restricted container/VM, mount only required paths, deny unnecessary egress, and apply the platform's seccomp/AppArmor/SELinux and filesystem controls. Never mount Docker sockets or host credentials into the service.

macOS tests exercise process separation, timeout, cancellation, permissions and output bounds, but macOS does not receive the Linux `RLIMIT_AS` memory control. Linux address-space enforcement and actual parser imports must be exercised inside the deployment image. Python/native libraries sometimes reserve address space beyond their resident memory, so do not infer suitable production limits solely from RSS. GeoJSON and subtitle validation remain bounded by upload size and their existing validators in the API; move those formats into the same restricted deployment boundary if the threat model requires every parser to be separately isolated.

File/image processor slots are shared among processes with the same UID and temporary filesystem. Separate containers with separate `/tmp` do not share that quota. Antivirus, file/image and FFmpeg slot budgets are independent; their per-child ceilings can add up to more than the host's available RAM. Set whole-container memory/CPU/PID limits and tune upload concurrency from measured peak use. A configured 1 GiB child ceiling is an upper bound, not reserved capacity or a guarantee that six simultaneous processor types fit a 4 GiB machine.

## Local evidence and target measurements

The final 2026-09-21 built-image HTTP preflight used 2 CPU cores, 4 GiB RAM and 256 PIDs: 50 independent display sessions completed 250 exact-result queries over the two-row CSV fixture with zero failures, p95 590 ms and maximum 701.77 ms. The same tool completed offline backup/restore and two subsequent app starts. See `test-evidence/phase-four/local-20260921/container-final/result.json`. The last `docker stats` sample is not a peak measurement. This local query result does not establish browser first paint, mixed-workload production capacity or target acceptance. Final processor/cache/scanner cancellation regressions passed 27 cases, and the final backend suite passed 848 with 15 integration tests deselected.

`tests/operations/test_processing.py` starts real child processes to verify environment scrubbing, output overflow termination, timeout reaping, cancellation, shared slot release, image timeouts and source/staging preservation. Existing file and media fixtures exercise CSV encodings, real Excel/Parquet, images, thumbnails and actual local FFmpeg codecs. Speech concurrent-session and recovery checks are documented in [speech-workers.md](speech-workers.md); backup recovery procedures are in [backup-restore.md](backup-restore.md).

The 2026-09-21 local run passed 86 processing/scanner/file/media tests on macOS and 86 on Linux Python 3.13.15 using the cached `datapulse-phase3-compose-smoke-datapulse` runtime with current server source mounted read-only. Linux used the unchanged 1 GiB address-space ceiling. The allocator diagnostic measured approximately 934 MiB virtual memory after parser imports with unrestricted glibc arenas versus 422 MiB with two arenas; resident memory was about 176 MiB in both cases. Logs are under `test-evidence/phase-four/local-20260921/`, including `linux-processing-followup-final.log` and `linux-parser-memory-diagnostic.log`. These are runtime checks against mounted source, not evidence that a newly built release image or production deployment passed acceptance.

The product baseline remains 2 CPU cores/4 GiB RAM, 50 viewing connections and approximately three seconds to initial player display, subject to the documented query limits. These are target acceptance measurements, not outcomes demonstrated by functional tests. Measure cold/warm player load, query latency, provider latency separately, memory/CPU peaks during mixed uploads/synthesis/viewing, queue waits, and cleanup after cancellation or worker death. Repeat under the real 4K display/browser/network configuration and the required eight-hour soak.
